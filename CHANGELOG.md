# Changelog

Notable user-visible, operational, compatibility, and security changes to ITAMbox are recorded here. Internal refactors and routine dependency updates are omitted unless they change supported behavior or deployment requirements.

This changelog follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Public tags use dotted prereleases such as `v1.0.0-alpha.1`; Python metadata maps the same identity to its PEP 440 form (`1.0.0a1`) where required.

## [Unreleased]

### Added
- Plugins can declare host-mounted REST resources using the Stable core model viewset bases and declare plugin-owned permission targets through `PluginConfig.permission_targets`. The host owns authentication, permission and schema defaults, rejects viewset overrides that bypass host authentication, permission checks or scoped list/detail handling, applies core tenant-scope rules after plugin queryset overrides and filter-backend processing, and includes declared targets in SSO role policy, Technician seed permissions and the tenant role matrix. Plugin GraphQL is query-only; writes use the host-owned REST surface.

### Changed
- Plugins are configured through `ITAMBOX_PLUGINS_CONFIG` (JSON keyed by plugin package) with per-key environment overrides `ITAMBOX_PLUGIN_<NAME>_<KEY>` for secrets, validated against the new `settings_schema` manifest attribute. `settings_schema` replaces `default_settings` and `required_settings`, which a plugin may no longer declare; unknown keys, missing required keys, wrong types and values outside `choices` abort startup with a message naming the plugin and the key, and keys flagged `secret` never appear in logs, diagnostics or errors. This includes the message of a startup error raised by plugin code and secret values of any length, including numbers.

## [1.0.0-beta.4] - 2026-10-13

### Added
- `manage.py operational_health` reports worker, scheduler, queue, cache, stuck-job and failure health with `--json` and `--check` (issue #587). Thresholds are configurable through the new optional `ITAMBOX_HEALTH_*` settings. `/health/` keeps its database-only readiness contract, now pinned by tests. Read-only; no migrations.
- `manage.py export_catalogue_schema` writes the JSON Schema (2020-12) of a community catalogue asset type, derived from the core specification vocabulary: flat model fields, `category` limited to the vocabulary categories, and a `specs` map limited to vocabulary keys with quantities in their vocabulary unit (for example `57 Wh`). The generated file is committed next to the generator and a drift test keeps it equal to the vocabulary (issue #769). The community catalogue repository [`itambox-community/type-library`](https://github.com/itambox-community/type-library) keeps a byte-identical copy and validates every model file against it (issue #771).
- The generic bulk import (preview, confirm, background job) imports catalogue asset types in that format (issue #770): each row's `specs` mapping is validated with the same rules as the generated schema before any job runs, `category` and `asset_role` are referenced by slug, a missing manufacturer is created only for an actor who may add manufacturers, rows are created through the canonical `create_asset_type` command, and an existing type is skipped and reported, never updated.
- The asset overview shows a compact **Recent activity** card with the five newest timeline events and a link to the full timeline (issue #645).

### Changed
- GraphQL schema introspection (`__schema`, `__type`) is now charged a flat cost of 50 per introspection root field by the fan-out complexity budget instead of per selected field, so the bundled GraphiQL loads its schema (docs explorer, autocomplete) instead of failing with `Query exceeds the maximum complexity of 2000.` (issue #813). Data selections keep the unchanged budget (max complexity 2000, fan-out 10), aliased repetition of introspection still exhausts it, and the token, alias and depth limits are unchanged.
- **Breaking:** The in-app Type Library is removed (issue #768). The **Type Libraries** navigation entry, the `/assets/type-libraries/` pages (list, import, detail, export) and the REST endpoints `POST /api/assets/type-libraries/preview/`, `/apply/` and `/export/` are gone and answer 404; library import, release history, reconciliation, snapshots and forks no longer exist. The read-only Library origin is no longer published: the `library` property of the REST Asset Type representation and the GraphQL `AssetType.library` field with its `LibraryOrigin` type are removed, and specification commands no longer lock library rows (the catalogue lock and the owner row lock are unchanged). The core vocabulary document drops its release envelope (`kind`, `library`) in favour of a plain `version` and `label`; its fields, fieldsets, choices and categories are unchanged. Reusable Asset Type models move to the community catalogue: one YAML file per model, imported through the regular bulk import (epic #772). The specification model is unchanged: managed core fieldsets, quantity kinds and units, ordered specifications with history and the core vocabulary keep working as before. The Asset Type columns `lifecycle`, `deprecated_at` and `replaced_by` existed only for the Library and are removed with it (they were neither shown nor filterable), and the `extras.manage_specification_library` permission and the Library model permissions are retired: the upgrade removes them from the permission table and from roles that carried them. No data migration is needed; Library tables are dropped empty.
- **Breaking:** Repair episodes are replaced by the repair maintenance itself (issue #644). The `RepairEpisode` model, its `/assets/episodes/` routes, its navigation entry, its form fields, its generic CSV export declaration and its permissions are removed; a repair is an ordinary `AssetMaintenance` of type *repair*, and that record anchors the whole story. Recording a repair can issue a loaner in the same submission: the loaner is checked out to the asset's current holder as a loan bound to that maintenance, with the due date defaulting to the expected completion, and the submission fails closed (writing nothing) when the unit is unavailable, belongs to another tenant, or the asset has no holder. Completing the repair offers *Returned* (the loaner is checked back in and the repaired unit is checked out to the same holder), *Replace permanently* (the loan stays with the holder as a regular assignment, optionally starting the disposal of the original unit in the same step, linked to the repair) or *Do nothing*; each reuses the existing checkout, check-in and disposal operations and their permissions, and an action the actor may not perform is not offered. `AssetAssignment` and `AssetDisposal` gain an optional `maintenance` link and the `episode` fields on maintenance, reservation and disposal are gone. The asset timeline groups records by repair maintenance and lists assignments and loans as events, and **Log repair** on the Timeline tab opens the maintenance quick-add with the repair type preselected. Upgrade: the migration maps every beta-era episode - a linked disposal moves to the episode's single repair maintenance, a linked stand-in becomes that repair's loan, and anything that cannot be mapped unambiguously (no or several repair maintenances, a reservation link, the episode notes, a substitute without a matching loan) is appended to the maintenance notes or written as a journal entry on the asset - reports the count per outcome, and leaves records that cannot be anchored standing and unlinked rather than dropping them.

- **Breaking:** GraphQL is read-only. All Graphene write mutations (assets, inventory, licenses, software, subscriptions and asset specifications, 54 in total) and their input types were removed, and the built-in schema publishes no mutation root. Writes are REST-only. Migration for API consumers: use the existing REST resources for assets, inventory, licenses, software and subscriptions (including the subscription lifecycle and assignment actions); asset-type composition and category defaults through the `asset-types` actions (`composition-preview`, `create-preview`, `apply-category-defaults-preview`); and the new `custom-field-choice-sets` and `custom-field-choices` resources, whose writes (like custom field and fieldset writes) now run through the definition commands with `If-Match` resource revisions. Money values are decimal strings or numbers on REST, which also resolves the former `createAsset(purchaseCost: 19.99)` Decimal failure (issue #612).

- The read-only GraphQL API moved from Graphene to Strawberry: `graphene` and `graphene-django` are removed and pinned to `strawberry-graphql` 0.328.x with `strawberry-graphql-django` 0.92.x (issue #613). The published schema keeps the previous contract unchanged — same `/graphql/` route, token authentication, locally bundled GraphiQL, introspection for authenticated users, and the same 24 root query fields with the same types, fields, argument names, and nullability. Four documented differences accompany the port: a plugin's `graphql_schema` now expects Strawberry `Query`/`Mutation` types instead of Graphene `ObjectType`s (the plugin API version stays 1.0, and a Graphene contribution is rejected and logged as a plugin failure instead of aborting core startup); the `Date`, `DateTime`, and `Decimal` scalar descriptions are reworded with unchanged wire behavior (`Date`/`Decimal` remain string scalars, `DateTime` stays ISO-8601); object types list their declared relations before the model fields and optional arguments print with an explicit null default (`after: Cursor = null`), leaving the type, field, and argument sets unchanged; and the former 500-field-selection cap is replaced by Strawberry's built-in `MaxTokensLimiter` (2000 tokens) and `MaxAliasesLimiter` (50) alongside `QueryDepthLimiter` (10) and the unchanged fan-out complexity budget (max complexity 2000, fan-out 10), while operations rejected before execution still answer HTTP 400 without a `data` member. `assets/tests/test_graphql_schema_snapshot.py` now pins the published SDL (fixture `itambox/assets/tests/data/graphql_schema_text.graphql`) together with the root-field contract.

- Generic CSV/YAML/template export is now explicit opt-in and scope-safe (issue #585). Every installed model carries a reviewed data-transfer declaration; an undeclared or denied model answers 404 on every generic export path (CSV, YAML, template render, `all`, `filtered` and `pk=` scopes) instead of being exportable by default. Each exportable model declares the scoping the export must apply (tenant-scoped manager, shared reference data, container scoping via `visible_to_containers`, or owner-scoped personal rows), and the route requires the model's dedicated `export_<model>` permission in addition to `view_<model>` wherever one is declared, so the generic surface is never weaker than a dedicated export. `compliance.CustodyReceipt` and the other confirmed or same-pattern surfaces (custody signing sessions and handoff deliveries, `compliance.AssetAudit`, attachments, `core.Job`, `core.RecycleBin`, personal dashboards/bookmarks, saved filters, webhook endpoints and deliveries, sessions, tokens, permissions, OTP devices and background-task tables) fail closed; their dedicated surfaces remain authoritative. Export templates bound to a denied model are hidden from the content-type picker and answer 404 rather than downloading an empty or over-broad file. `export_scope=all` now documents and implements "every row the requester may see under their declared scope", never every row in the database.

- `reconcile_procurement_legacy` reports pre-upgrade fulfilment pledges (requests that a partial receipt approved while delivered quantities were still untracked, with a blank `qty_received`); it classifies each pledge individually: candidates are pledges on partially received non-serialised lines whose own allocation exceeds the line's recorded received quantity, while completed records (assigned asset or fully received line) stay untouched and pledges the received units could cover in full, lines without receipt, and serialised lines without an asset require explicit operator review - `--apply` only softly closes the candidates without rewriting any recorded quantity, stock, or approval state; the affected units can be re-requested (issue #569).

- Tenant SCIM `DELETE` now unlinks the user's active AssetHolder instead of soft-deleting it, preserving the holder detail page, offboarding report, assignments, and other obligations. Tenant create/update use the shared exact-identity holder policy, which rejects email-only matches when UPNs differ and does not overwrite an existing holder's profile; provider SCIM remains membership-only (issue #608).
- Bulk import is now an allowlist. Only models with a declared, curated import form are importable (assets, asset types, manufacturers, accessories, consumables, licenses, locations, asset holders, subscriptions); every other model, including assignments, custody receipts, and signing sessions, answers 404 on the import route instead of being written through reflection. Updating existing rows through import is now restricted: the `id` column is ignored, a row updates an existing record only through a declared natural key (asset `asset_tag`, manufacturer `name`, asset holder `upn`), and only for an actor holding `change` permission on that record; add-only roles can no longer rewrite existing rows. Required foreign-key columns no longer fail every create (issue #605).
- Removed the legacy CSV shape and grandfathered marker from Report Templates. Live templates still using that shape must be resolved before upgrade or the migration refuses with every affected name and PK; custom HTML remains sandboxed, and reverse is refused in favor of restore-first rollback (issue #586).
- The production Compose `db` and `valkey` services now use reviewed multi-platform index digests alongside their readable tags. This prevents upstream tag movement from changing bundled service images and extends reproducible pinning to build and CI images; operators using managed PostgreSQL or Valkey can use the documented Compose override (issue #582).
- **SCIM Provisioning** is promoted from **Beta** to **Stable**: both mounts are always available, the published capability carries no activation probe and no limitations, and the supported SCIM 2.0 subset (endpoints, operations, PATCH paths, filter grammar, error envelopes, and `ServiceProviderConfig`) is frozen for tenant- and provider-scoped mounts (issue #571). Nothing provisions automatically — provisioning still requires an operator-minted, scope-bound, write-enabled token and an identity provider that deliberately calls the mounts, and least-privilege behavior is unchanged. The tenant mount now shares the provider mount's strict request parser: unsupported PATCH operations and paths answer SCIM `400` errors instead of being silently ignored, bracketed `emails[type eq "work"].value` paths are applied, and a rename onto an existing username answers `409` with `scimType: uniqueness` instead of a server error. Deactivate, reactivate, deprovision, and reprovision are frozen as one lifecycle: inactive resources stay addressable and reactivatable on both mounts, and a re-provisioning `POST` restores login without a manual account edit. No schema migration accompanies the promotion; existing `scim_id` / `external_id` mappings, memberships, group rows, and tokens are preserved.
- **Asset Request Procurement Seam** is promoted from **Beta** to **Stable** and becomes always available: manual procurement no longer depends on the optional `ITAMBOX_REQUISITION_AUTO_APPROVAL_THRESHOLDS` setting, which keeps governing automatic approval only. The published capability carries no activation probe and no limitations (issue #569).
- **Webhooks and Event Rules** is promoted from **Beta** to **Stable**: the capability is always available, carries no activation probe, and its envelope contract is graded Stable. Nothing about delivery timing changes — nothing is ever sent until an administrator deliberately creates and enables a webhook endpoint and an event rule; an endpoint alone activates nothing. The published event vocabulary now matches the emitted one: `create`, `update`, `delete`, `restore`, `checkout`, `checkin` (the previously published three-value `core.EventActionChoices` enum was a stale legacy artifact); the vocabulary stays open for additive values in minor releases. The minimal `data` metadata (`app_label`, `model_name`) is stated as the explicit V1 promise — no object snapshot is promised and consumers must tolerate additional members. HMAC signing (`X-Hub-Signature-256`), the reduced Slack/Teams payload guarantees, tenant scoping, SSRF protection, and delivery-history permissions are unchanged. No schema migration accompanies the promotion; existing endpoints, rules, and delivery history are preserved (issue #566).
- Webhook deliveries now retry HTTP **429** responses within the configured retry budget instead of failing terminally, and honor a valid `Retry-After` header (delta-seconds or HTTP-date, capped at 300 seconds, with `0` meaning an immediately due retry) when scheduling the next attempt; absent or invalid headers fall back to the endpoint's normal backoff policy. Pending rate-limited attempts are recorded with the `integration.rate_limited` error class. Redirect (**3xx**) responses are never followed and are recorded as terminal non-deliveries instead of successes, and test sends keep the reserved `event` value `test` while carrying the same minimal `data` metadata as event deliveries (issue #566).
- Promoted the Report Designer from Beta to Stable and made it always available. Its V1 contract for report type, included columns, filters, and grouping is frozen; migrated grandfathered templates keep rendering and are editable through the supported upgrade path (issue #565).
- Removed `ITAMBOX_FEATURE_REPORT_DESIGNER` and its historical alias `ITAMBOX_REPORT_DESIGNER_ENABLED`; designer routes and downloads no longer require an activation flag (issue #565).
- Upgrading a deployment that ran the designer disabled (flag unset or false) pauses registered, active, non-grandfathered schedules that were being skipped: the one-time transition removes their django-q row and keeps every row and its delivery history, and delivery resumes only after an explicit re-enable in **Extras → Scheduled Reports** — so removing the flag cannot silently resume suppressed outbound delivery. Keep `ITAMBOX_FEATURE_REPORT_DESIGNER` in place through the first upgraded start; the transition reads it once and ignores it afterwards (issue #565).
- The **Reporting** menu group no longer carries the Beta badge; with Scheduled Reports also promoted in this release (below), no reporting surface carries a Beta badge anymore (issues #565, #570).
- Report compilation is capped at 500 rows per provider (per catalogue for Hardware Inventory) and discloses capped windows or sample output in rendered files, scheduled mail, and download headers. Machine-format exports remain free of in-file disclosure rows and cover the compiled window; requesting `machine_csv` without machine-export support returns HTTP 400 (issue #565).
- **Alert Rules and Channels** is promoted from **Beta** to **Stable**: the capability is always available, carries no activation probe, and its V1 contract is frozen — six alert types with the documented threshold semantics, daily state-based evaluation, renotification intervals, muting, auto-resolution, and the single-attempt best-effort delivery policy. Stable availability changes nothing about notifications: no alert rule or channel is ever created or enabled automatically, and nothing is delivered until an administrator deliberately creates an active rule with attached, enabled channels. The two former Beta limitations — evaluation is daily rather than continuous, and channel delivery failures are logged rather than retried — are restated as steady-state V1 behavior in the operator guide. No schema migration accompanies the promotion; existing rules, channels, alert history, and delivery state are preserved (issue #567).
- Alert channel delivery now honors the channel **Enabled** flag and the rule's channel scope: a disabled channel is never contacted, and if every attached channel is disabled the alert records an explicit reason with outcome `none` instead of a silently successful delivery. Rules reject channel attachments outside their own scope at the form and API boundaries (a tenant rule accepts only its own tenant's channels; a platform-wide rule only platform-wide channels), and dispatch ignores out-of-scope attachments so a misconfigured row cannot deliver across scopes. The dispatch claim is atomic and leased (15 minutes), so parallel evaluations planning a dispatch for the same alert state deliver exactly once, an in-flight attempt is never re-dispatched by a parallel evaluation, a crashed claim is still recovered after the lease expires, and completion metadata is fenced to the owning delivery id; the alert rule form's channel choices are scoped to the channels the actor can reach. The read-only alert REST endpoints and the delivery-outcome filter are unchanged, and the alert-type vocabulary stays open for additive values in minor releases (issue #567).
- **Scheduled Reports** is promoted from **Beta** to **Stable**: the capability is always available, carries no activation probe, and the V1 scheduling contract is frozen. Supported frequencies are once, hourly, daily, weekly, biweekly, monthly, quarterly, yearly, and custom cron with save-time cron validation. Cadence math runs in the deployment's cluster time zone and preserves the local wall-clock time of daily, weekly, monthly, and quarterly cadences across daylight-saving changes; monthly, quarterly, and yearly steps clamp to month ends. After worker downtime, each scheduling pass replays the oldest missed occurrence once before advancing the cadence, the list shows the next run per schedule, cadence edits re-anchor the next run while metadata-only edits keep it, and deactivating removes the background row while reactivating re-registers it. Stable availability activates nothing: no schedule row is created, no next run is rewritten, and schedules that the #565 transition paused stay paused until an operator re-enables them (issue #570).
- Scheduled-report fires are now claimed per exact occurrence time before any work: a broker redelivery, a duplicated queue entry, or a worker restart is a recorded no-op, and an out-of-order replay (a newer occurrence accepted first, as parallel workers can produce) never discards an older, still-unaccepted one. Each run records generation, archive, and per-channel delivery outcomes separately: the archive row carries a per-target delivery ledger (email aggregate plus one entry per notification channel) and a delivery status (`none`, `success`, `partial`, `failed`), the schedule's last status distinguishes `success`, `partial`, and `failed`, and a new **Retry delivery** action re-attempts exactly the targets recorded as failed, replays the recorded original recipients, email subject/body, and notification payloads even if the schedule was edited since, re-validates the archived run's generation scope against the standing approval, is refused while the schedule is inactive, binds to the newest run's own archive (a run that retained no archive is refused instead of redelivering an older report), and serializes parallel attempts with an exclusive, self-expiring claim whose fan-out renews it before every target, aborts once it was lost, and keeps outbound attempts bounded so overlap is limited to a single in-flight send. A file-write failure during archival marks the created archive failed instead of leaving it running, and a failed generation attempts no delivery at all. Schedule-level summary writes are fenced to the newest started run, so an older overlapping occurrence can never overwrite a newer run's status or retry binding: the shared start marker advances atomically and only forward, so even a delayed older occurrence persisting its start after a newer one keeps running for its own archive and ledger yet can never reclaim the fence; a retry completion is fenced to its archive still being the newest binding (issue #570).
- The scheduled-reports upgrade carries a non-destructive transition: every registered report schedule row gains the fire-identity task keyword so redelivery is a no-op from the first fire after the upgrade, duplicate registration rows for one schedule are collapsed onto the row the schedule references (falling back to the oldest), with references to a removed duplicate re-pointed, archive rows gain the delivery-ledger columns, each schedule's newest accepted occurrence is registered as a fire record so idempotency stays exact-match per occurrence across the upgrade, and the archive gains the generation-scope snapshot plus the retry-claim columns, and each schedule gains the retry binding that ties **Retry delivery** to the newest run's own archive (pre-promotion rows stay unbound so the action is unavailable until the next completed run; old failures are recovered with **Run now**). Activation state, next-run values, approvals, archives, and other schedules are preserved; the migrations reverse cleanly (the keyword is cleared again because a downgraded task signature does not accept it), and collapsed duplicates are not resurrected (issue #570).

- Deleting an asset holder is now a coordinated archive instead of a single-row soft delete: it refuses while any open obligation exists (active asset assignments, open accessory, component and consumable checkouts, held license seats, open asset requests, live reservations and pending custody signing sessions) and reports what is blocking, clears the holder's user link and ends the subscriptions covering the holder, and leaves closed assignments, custody receipts and journal entries untouched. The same service serves the holder delete form, bulk delete and the REST API, replacing a view-level guard that only inspected asset assignments, so an active assignment can no longer be left pointing at an archived holder. Recycled holders restore through the same service, which revalidates the `(tenant, upn)` unique slot and reports the conflict instead of failing with a server error (issues #608, #619).

- Deleting a location is now a coordinated archive instead of a single-row soft delete (issue #619). It refuses, with nothing written, while live assets, active asset assignments, open inventory checkouts, stock rows with remaining quantity, live child locations or open purchase orders still depend on the location; empty stock rows are archived with it and a restore brings back exactly the rows that archive moved. Open asset requests and open audit sessions are detached from the location, subscriptions covering it are ended, and closed requests, finished audits, audit results and journal entries are kept. Schema: `ComponentStock`, `AccessoryStock` and `ConsumableStock` gain a leaf `deleted_at` with an archive-operation marker and their location uniqueness constraints become active-rows-only; existing rows are preserved with no backfill.
- Deleting a kit or a subscription is now a coordinated archive instead of a single-row soft delete (issue #619). Archiving a kit archives its items with it - the generic cascade destroyed them, so a recycled kit came back without its definition - and archiving a subscription archives the assignments that say who it covers and unlinks every license that names it as its funding agreement, each touched row with its own audited change. Journal entries, attachments and the detached licenses keep their history, and a kit item or subscription assignment deleted on its own is never resurrected by a restore. The same services serve the kit/subscription delete form, the subscription bulk delete and the REST API, and the recycle bin restores through them: a restore revalidates the active name/slug unique slot and the active assignment target and reports the conflict instead of failing with a server error. Schema: `KitItem` and `SubscriptionAssignment` gain a leaf `deleted_at` with an archive-operation marker, the kit list counts live items only, and the assignment uniqueness constraint becomes active-rows-only; existing rows are preserved with no backfill. Soft-deleting an object that a subscription assignment covers (an asset, holder, location, accessory, component or consumable) now archives that assignment with it instead of physically destroying it, matching the leaf flag the assignment carries.
- Deleting an asset is now a coordinated archive instead of a single-row soft delete (issue #619). It refuses, with nothing written, while the asset has an active assignment (as the assigned asset or as an assignment target), open maintenance, a live reservation, a held license seat, or an open accessory, component or consumable checkout. Open requests are cancelled, subscriptions are ended and the asset leaves its contracts; closed assignments, finished maintenance, warranties, finished reservations and installed-software records are archived with the asset, and a restore brings back exactly the rows that operation archived. Disposal evidence is kept. The upgrade adds an archive-operation marker to those history tables and a soft-delete column to installed software; existing rows are unchanged.
- Deleting a tenant is now a coordinated archive instead of a single-row soft delete (issue #619). It refuses, with nothing written, while live business records or live child tenants still belong to the tenant. Roles, user groups, event rules, webhook endpoints, report templates, notification channels, alert rules, saved filters and asset tag sequences are archived with it and a restore brings back exactly the rows that operation archived. Resource grants to or from the tenant are revoked and a restore does not re-grant them; memberships and tokens are kept and inert while the tenant is archived. Schema: those configuration tables gain an archive-operation marker; existing rows are unchanged.
- Purchase orders, licenses, and accessories, components and consumables are archived through per-aggregate services as well (issue #619). A purchase order refuses while a line still carries a live fulfilment link, archives its lines and detaches linked contracts; a license refuses while a seat is held or a live kit item lists it; an inventory item refuses while it has open assignments, stock with quantity, or a live kit item, archives its empty stock rows with it and cancels its open asset requests. Restores bring back exactly what the operation archived. The generic soft-delete cascade is gone: archive handlers carry the cascade semantics, and a new system check (`core.E004`) requires every soft-deletable model with child relations to be a registered archive root or a declared leaf. Plugins that define soft-deletable models with children must register an archive handler or declare the model as a leaf.
- Asset issuance eligibility is one rule shared by checkout, bulk scan, request fulfilment, kits, licenses and subscriptions (issue #610). **Deployed** is the checkout/check-in lifecycle status: an active assignment requires it, and pending, approved and procurement-stage requests all count as open for duplicate detection.
- System-initiated writes carry an audit identity (issue #614): every mutating management command (`bind_oidc_identity`, `import_snipeit`, `prune_changelog`, `purge_deleted`, `reconcile_procurement_legacy`, `restore_resource_grant`, `rotate_encryption_keys`, `run_jobs`, `seed_data`, `sync_intune`, `sync_tenant_ldap`) runs inside an actorless system execution context, so its changes appear in the change log instead of being dropped. A change-logged save without any execution context now raises in development and test runs and is logged at `WARNING` in production.
- Event rows are recorded only when an enabled, live, actionable event rule exists for the model, the object's tenant (or a global rule) and the action (issue #621). Saves without a matching rule no longer write an `Event` row or take the rule lock; the webhook envelope and delivery contract are unchanged.
- Tenant scoping of forms, filter forms and admin forms is declared explicitly (issues #584, #618): the global runtime patches of Django's `ModelChoiceField.queryset` and `BaseForm.__init__` are removed, and core forms use `TenantScopedFormMixin`, the tenant-scoped field classes and `TenantScopedFilterSetMixin`. Plugin forms that relied on the implicit patch must adopt these abstractions to keep their choice lists scoped.

### Fixed

- Custody receipts are now bound to the custody period they evidence: signing refuses a receipt whose period has ended with `custody_superseded` (HTTP 410), and checking in or reassigning an asset closes the holder's still-pending receipts as the new terminal state `superseded` instead of leaving them signable forever. Accepted and declined receipts are never rewritten, open signing sessions of a closed period are canceled, and a new nullable `CustodyReceipt.assignment` link records the evidenced period, backfilled where unambiguous and left empty where the history does not identify one. Holders who are not members of the asset's tenant can sign again: acceptance no longer rewrites the asset row through a save that re-runs tag allocation and tenant-scoped validation (issue #607).
- Partial purchase-order receipts no longer approve every linked request at once: a receipt attributes the delivered quantity per fulfilment link, serialised request units receive exactly one asset per delivered unit and are approved only on full delivery, genuinely quantity-bearing requests (components, accessories, consumables) are approved only once their full reserved quantity has arrived, attribution follows the oldest open request on the line, and surplus units beyond the reserved demand stay as free stock. Cancelling a request closes its still-unreceived fulfilment links while the delivered quantity stays on record and the purchase-order line is left untouched; requests for multiple serialised units can no longer be linked to a purchase order and must be split into request units first. One schema migration adds the per-link received quantity (`FulfillmentLink.qty_received`), blank on links that predate it; those keep their reservation and complete on their next full receipt, so no historical quantities are invented (issue #569).
- Partial-receipt submissions carry a receipt-state snapshot: every receipt states the recorded quantities it was prepared against, and a submission whose lines have moved on (a retry, double-click, replay, or parallel duplicate of the same operation) is refused before anything mutates instead of silently booking additional stock. The receive form binds the snapshot into each rendered form so every submission carries its own copy (a later render, another tab, or another order never re-validates an already-issued submission), and a freshly rendered form can be submitted against the current state; the REST receive action requires the matching `expected_received` field next to `line_quantities` (issue #569).
- Bulk import accepts rows without a slug column: the slug is generated before validation for auto-slug models (issue #766) and for the Manufacturer and Location import forms, which advertise an optional slug (issue #784); generated slugs are bounded to the field length including collision suffixes, while an overlong supplied slug is still rejected (issue #786).
- Malformed CSV rows with extra cells and YAML documents with non-mapping list items report indexed validation errors in the preview instead of a server error; an invalid preview stores no rows and enqueues no job (issue #785).
- Active `Consumable`, `Accessory` and `Component` uniqueness is scoped per tenant on `(tenant, manufacturer, name)`, with a separate global uniqueness for tenantless catalogue rows, so a tenant can stock a product another tenant already holds; a same-tenant duplicate is reported as a form error (issues #767, #783).

### Security

- Report provider domain permissions are now enforced at one central compile boundary for preview, download, and scheduled runs. Every declared permission is required for every tenant in the effective scope, including all three inventory permissions for Hardware Inventory; missing or unresolved authorization fails closed. Aggregate scopes resolve the same effective tenant set the scoped querysets read: the accessible set under "All accessible tenants", the reachable tenants of the active tenant group; only a truly global (unscoped) context is evaluated against every live tenant. Interactive preview and download denials return HTTP 403, while scheduled denials record `terminal: report.permission_denied` and create no archive or delivery. **Run now** always evaluates the invoking user for single-tenant and broad schedules alike, against both the persisted scope's tenant reach and the provider's declared domain permissions; only an unattended broad run evaluates the recorded scope approver. Unattended single-tenant schedules require explicit system authorization, and active superusers pass. This deliberately denies principals who previously had template or schedule access without permission to read the report data (issue #581).
- Pinned report scopes are authorized at compile time: one pinned tenant must be within the actor's reach, and multi-tenant scopes require `reports.view_cross_tenant_reports` for every pinned tenant. Unauthorized preview or download returns HTTP 403; scheduled generation is denied and is not delivered (issue #565).
- Cross-tenant report compilation runs under an explicit authorized scope: the ambient request tenant no longer truncates a pinned constellation before its authorized filter applies, so a single pinned tenant compiles exactly that tenant and an authorized multi-tenant aggregation compiles every pinned tenant; unauthorized constellations still fail closed before any provider runs (issue #565).

- Alert deliveries can no longer cross tenant or platform scopes: dispatch consults only channels inside the rule's own scope, out-of-scope channel attachments are rejected at the form and API write boundaries, and an attachment that could never deliver now fails predictably instead of being silently ignored.
